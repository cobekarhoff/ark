# v1 trusts the operator's OS user; integrity checks catch mistakes, not forgery

In v1, agents run as the operator's OS user, with shell access to every file that user can write: run folders, the ledger, state.json, ~/.ark, ~/.bun and git config. A process with that access can rewrite any check's inputs: rechain the ledger, append a forged `gate.answered` line, edit the cached state, replace the `bun` binary, or record `implementer.completed` for code it wrote itself. No check that lives in the same files can stop that. So Ark's integrity mechanisms (owned events, the hash-chained ledger, attribution of worktree changes, clean-checkout proof, the tool-call hook, terminal-confirmed answers in ADR 0002) are designed to stop an honest-but-mistaken agent and to detect corruption. They are not designed to withstand an agent deliberately tampering as the same user.

What actually bounds a hostile agent in v1: GitHub branch protection on the default branch (PRs only, CI required, admins included, no force push), the cross-vendor review panel, and the human's review of diffs and evidence at G2 and at merge.

We considered an OS sandbox for agent tools (Seatbelt/bubblewrap, write access limited to the worktree) and a signed ledger with a Keychain key that needs Touch ID. Both are deferred. Revisit before Ark is used on regulated production tickets (NFR-05) or on a shared runner; ARK-118's spikes are the starting point.
