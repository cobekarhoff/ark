# Why Master Chief reads some messages late

> Spike report, measured 2026-11-07. A snapshot, not current behavior. Outcome: Fix 1 shipped as ARK-352, so `skills/ark/playbooks/chief.md` now says to never use the blocking `ask` tool for a gate. The note below that `chief.md` still tells Master Chief to `--ack` is obsolete.

ARK-347 spike. Measurement and recommendation only: the spike itself changed no product code, playbook or setting.

## Summary

- Of the 296 question, escalation and status messages sent to Master Chief's Run in the inbox, 27 (9.1%) waited more than 15 minutes. Together they waited 4,903 minutes (81.7 h).
- 26 of the 27 (99.0% of the wait, 4,853 min) arrived while Master Chief was inside its `ask` tool, relaying a gate to the human. A blocked `ask` holds Master Chief's whole turn, so nothing else is read until the human answers. The wait is the human's answer time on another gate, not a slow reader.
- 1 of the 27 (50 min, 1.0%) arrived while Master Chief's own model request had failed with HTTP 429. The session sat idle until the human typed `continrue`.
- No late message was caused by a long `check --wait`, a long tool call, a context handover, a human conversation, a dropped Run binding, an Orca outage or a missing session.
- A missing `delivered_at` does not mean a fast read: 9 of the 195 undelivered messages waited over 15 min (2,942.5 min), all behind an `ask`.
- The 1-in-10 figure in the ticket comes from messages that have a `delivered_at`. Only 101 of the 296 have one. Over all 296, 6 of 131 questions (4.6%) waited more than 87 minutes, and 16 of 131 (12.2%) waited more than 15 minutes.

## What `delivered_at` means

`delivered_at` is **the time Orca pushed a "you have mail" pointer into the receiver's terminal or session**. It is not the time the agent read the message. A message that the agent reads with `orca orchestration check` is marked `read = 1` and gets no `delivered_at`.

Source (Orca 1.4.250, `Orca.app/Contents/Resources/app.asar`, `out/main/chunks/orcad-migration-source-retention-CwgUFZi4.js`):

- The push path sets it: `UPDATE messages SET delivered_at = datetime('now'), pointer_enter_pending = 0, pointer_pty_id = NULL, pointer_process_incarnation = NULL WHERE to_handle = ? AND id IN (...)` (`markAsDelivered`). A structured agent session gets the same call when Orca hands the message to the session (`index.js`: `f&&!f.delivered_at&&t.markAsDelivered([c.message_id],n)`).
- Messages still waiting for a push are the ones selected with `read = 0 AND delivered_at IS NULL AND pointer_enter_pending = 0 AND delivery_contract = 'current_delivery'`.
- The read path does not set it: `markAsRead` runs `UPDATE messages SET read = 1, pointer_enter_pending = 0, pointer_pty_id = NULL, pointer_process_incarnation = NULL WHERE id IN (...)`. No `delivered_at`.
- Two minor writers: a heartbeat gets it at insert time, and the legacy acknowledge path (`markAsReadAndDelivered`) sets `read = 1` and `delivered_at` together.
- The pointer text is built by `oft`: "You have N orchestration messages. Run `orca orchestration check --run <run id>`."
- `orca orchestration check --help`: "A consuming check marks the batch it returns as handled, so the next check returns newer mail; no --ack is needed."

Command output that confirms it, from the snapshot and the Master Chief session files:

- Of the 101 delivered question, escalation and status messages to Master Chief's Run, **101** have a "You have N orchestration messages" line in a Master Chief session file within 60 s after `delivered_at` (133 of 133 with `worker_done`). Of the 195 without `delivered_at`, 6 have such a line near their created time, by coincidence.
- Example: `delivered_at` `2026-11-06T06:14:52Z`; session line at 06:14:54, `USER: You have 3 orchestration messages. Run `orca orchestration check --run run_b8687a63b62e`.`

The pointer is typed only when the agent can take input. While Master Chief is inside `check --wait` or a tool call, the message is read by that `check` and never gets `delivered_at`. While it is inside `ask`, the pointer waits until the `ask` returns, which is why the 17 late rows that have a `delivered_at` carry one that is 0-5 s after an `ask` result. The other late rows have none: the nine ask-gate rows 3-10 and 21 (2,942.5 min in all, e.g. `msg_68d723581bf6`, created 11-01 03:48:22, first seen 15:51:14) were consumed by the next `check` after the `ask` returned, 0-31 s after it, before any pointer was recorded; and row 20 was injected as an async `check --wait` result. [INFERENCE] The read beat the push: no Orca log I read shows the push for these nine.

### Why 1,332 of 1,742 messages had no delivered time

The same count at the snapshot is 1,365 of 1,858 (73.5%; the ticket's figure was 76.5%). Breakdown:

- 1,347 of the 1,365 have `read = 1`: an agent consumed them with `check` (or an async `check --wait` result) before, or without, any pointer push. By type: `worker_done` 941, `status` 250, `question` 98, `escalation` 50, `heartbeat` 8.
- 18 are still unread and unpushed (`read = 0`).
- Delivered messages are the minority, 493 in all (487 of them read after the push).

A missing `delivered_at` means only that Orca recorded no pointer push. It does not mean the read was fast, and it does not mean the message was read:

- Consumed (`read = 1`, 1,347 of the 1,365): the agent read it without a recorded push. Most were read at once, but not all. Of the 195 undelivered messages to Master Chief's Run, the measured median wait (pickup time minus created time) is 0.0 min, and that median is the only fast-case claim this file makes. Nine of the 195 waited over 15 min, behind an `ask` (see above).
