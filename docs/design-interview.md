# Ark design interview

Status: interview complete (Q44 confirmed). Outputs: [design-spec.md](design-spec.md), [skill-extraction-plan.md](skill-extraction-plan.md), [build-plan.md](build-plan.md). No implementation authorized yet.

## Settled decisions

1. **Clean rewrite.** Do not reuse anything from the existing `software-factory` repo: implementation, glossary, ADRs, prompts, skills, or design decisions. Earlier comparisons are not requirements for ark.
2. **Per-product configuration.** Ark is a generic standalone tool. Each agentic environment owns its product configuration in `ark/`, alongside its knowledge base and product repo clones. The pilot environment is the first target and a second environment is a later one; the engineer-agent template can support future environments.
3. **Skills.** Ark owns the shared `ark-*` core skills, with versioning and evals. Agentic environments supply product-specific add-on skills through role manifests. Existing overlapping environment pipeline skills retire after cutover.
4. **Risk/QMS split.** Ark owns the deterministic risk-classification mechanism and conditional gates; environments own rules and traceability content. Risk cannot be downgraded automatically; classification against the actual diff takes the higher result. Changes to risk rules are high-risk.
5. **Arbiter (revised during Q14).** A separate CI/CD reviewer for published MRs, not the local pre-QE reviewer. Ark's local review role or agents should adapt pstack's approach through our own `ark-*` skills. The previous decision to invoke Arbiter locally is superseded. Arbiter's CI integration contract remains to be specified.
6. **Intake rollout.** Local ticket input now. Jira integration when the operator returns from leave. Jira synchronization, polling, source-change handling, and write-back behavior are not yet decided.
7. **Verification environments.** Local real application services and databases, with a cloud emulator (LocalStack-compatible) for cloud dependencies, are sufficient for acceptance. If an agentic environment already provides a quick ephemeral-deployment task, ark may use it for iterative E2E verification. Ephemeral cloud deployment is an optional project capability, not a universal prerequisite. Evidence must identify the environment used; local green does not certify cloud parity.
8. **First pilot.** One service or app in the pilot environment; the first ticket must not require coordinated source changes across product repos. The exact service and ticket remain to be selected.
9. **Acceptance authoring.** A separate Acceptance Author creates executable acceptance checks and records the four test-value answers during planning. The human approves the plan and checks together before build. The Builder cannot edit approved checks; QE runs them.
10. **Permanent check ownership.** Acceptance checks live in the product repo whose contract they protect. Cross-repo scenarios without a natural owning repo live in the agentic environment. Approval pins the verification inputs, including test helpers and fixtures; run folders retain evidence and references, not the sole regression-test copy.
11. **Execution and harness independence.** Local-first workstation execution. Neither OMP nor Herdr is required. Ark must support any harness through an adapter contract; Claude Code and OMP are the first two in use. Herdr may provide optional terminal visibility and attachment, never core orchestration or authoritative state.
12. **Permission enforcement.** Hard filesystem isolation enforced outside the harness. Builders receive writable source and protected read-only acceptance inputs; QE receives read-only source/checks and writable evidence output. The exact isolation technology remains undecided. Verification-service provisioning belongs to trusted infrastructure, not unrestricted agent access to the host Docker socket.
13. **Provider policy.** The first pilot may send code and artifacts only through explicitly approved enterprise model-provider routes. Harness choice does not authorize a provider route. The approved endpoints/accounts and available models have not yet been identified.
14. **Configurable local review.** A pstack-inspired reviewer panel plus Review Lead, with the same rubric given to independent reviewer sessions. Model-family diversity is not mandatory. Each engineer can configure their review arrangement to match available models. The exact configuration layering and minimum reviewer count remain unresolved; Builder/QE flexibility is settled in decision 15.
15. **Builder/QE model flexibility.** Prefer different models, but permit explicitly configured same-model verification. QE still receives a fresh isolated session and reruns the locked checks in a clean environment. The effective manifest and dashboard disclose same-model verification; no silent fallback. Model-family diversity is not required.
16. **Repair cap.** One shared configurable cap across accepted local-review blockers and confirmed QE defects. Default three failed rounds total; reaching the cap escalates before another automatic Build round. Intermediate success does not reset it. Engineers may tune it within the project's pipeline policy.
17. **Concurrency.** Concurrent planning/build/review agents in isolated worktrees, with configurable agent limits. Verification uses environment-resource leases and queues behind one slot by default; projects that support isolation may advertise more slots. Each verification run still uses a fresh environment.
18. **Post-publication repair.** Accepted blocking Arbiter findings return to Build and consume the same shared failure budget as local review and QE. Any changed source head repeats local review, clean QE, and CI before final human approval. CI infrastructure failures are not automatically classified as source defects; approved-check changes retain their separate human gate.
19. **Merge authority.** Ark prepares verified MRs, tracks readiness/dependency order, and observes landing. Engineers execute merges in GitLab; ark does not merge under the initial policy. Cross-repo completion must track actual landed revisions and dependency-artifact availability, not approval alone.
20. **Configuration authority.** Engineer preferences operate within environment policy. Engineers may select models, harnesses, reviewer counts, and resource/retry settings within product limits. Human gates, risk rules, approved-check policy, and merge authority belong to the versioned agentic-environment configuration; personal profiles cannot bypass them.
21. **Human interfaces.** Ark dashboard and CLI resolve plan, approved-check-change, escalation, and QMS gates through the orchestrator's decision interface. Final MR approval and merge occur in GitLab; ark observes and displays their status. No duplicate ark final-MR approval is required.
22. **Notifications rollout.** First slice uses the local needs-human queue and workstation notifications. Slack/phone notifications remain required later delivery items; their channel and remote-access policy are not yet selected.
23. **Eval integration (superseded by Q42).** Removed. No factory eval executor or external AI eval integration is required.
24. **Eval promotion (superseded by Q42).** Removed. No factory baseline-promotion or agent-quality regression gate is required.
25. **Profile qualification (superseded by Q42).** Removed. Engineer model/harness preferences require policy/contract validation, not full-suite eval qualification.
26. **Durable evidence.** Published evidence uses GitLab-native retained bundles with explicit project retention and access controls. MRs link to exact-head bundles and checksums. Transient CI-job links alone are insufficient; QMS record-store suitability must be established separately. Credentials and sensitive headers are redacted before persistence.
27. **Reflection.** Knowledge/skill improvement proposals come from a separate scheduled/on-demand pipeline over completed runs, not mutation of active ticket scope or pinned skills. Proposals land through review in their owning repos. There is no skill-eval qualification prerequisite after Q42.
28. **Cross-repo binding.** Agentic environments declare dependency edges and tasks that build/install exact artifacts, pin submodule references, or connect changed services. Ark executes those tasks against pinned revision vectors and records the bindings for combined verification. It does not implement a universal package-management strategy. Consumer readiness must be refreshed against actual landed revisions/artifacts.
29. **Plan flexibility.** Builders may record and make implementation-detail deviations within approved behavior, repo/path scope, check contract, and risk constraints. Material behavior/scope/check/architectural/security changes require plan amendment and human reapproval. Uncertainty escalates; it does not silently widen scope.
30. **Core stack.** TypeScript on Node.js for the clean-rewrite core, CLI, adapters, and web-dashboard contracts. No OMP or Bun runtime dependency is implied. Verification remains project-owned commands rather than a prescribed language or agent framework.
31. **Ledger.** SQLite with an append-only events table and rebuildable projections. The orchestrator validates authoritative transitions/approvals. Role lifecycle emissions, harness telemetry, and file-watch events are attributed observations, not permission to advance stages merely because an agent reports done.
32. **Generated layout.** Each agentic-environment clone keeps committed configuration in `ark/` and generated gitignored data in `.ark/`. Runs use `.ark/runs/<ticket>/<run-id>/`; worktrees use `.ark/worktrees/<ticket>/<run-id>/<repo>/`. One per-engineer local SQLite ledger indexes registered environments. Repeated ticket runs never overwrite prior evidence.
33. **Artifact authority.** Stage contracts use canonical JSON with runtime schema validation and referenced artifacts. Markdown documents such as ticket.md, analysis.md, and plan.md are generated human-readable views, not a second editable source of truth. Approval pins canonical inputs and referenced executable checks.
34. **Pipeline extensibility.** Versioned pipeline.yaml composes typed agent-role, deterministic-command, human-gate, and external-status-wait stages. Contracts, permitted roles, conditions, transitions, and bounded retries are declared and validated against environment policy. Product add-on stages do not require hardcoding their workflow in ark. No embedded JavaScript or LLM-selected routing.
35. **Manual intervention.** Explicit takeover/hand-back: stop the active writer and record its interrupted attempt before granting engineer ownership. On hand-back, record the changed revision and re-enter review/clean verification. Material changes reopen approval. Observation alone does not require takeover.
36. **Skill ownership.** One owning role means maintenance/contract responsibility, not exclusive execution. Other explicitly declared roles may consume the skill through validated contracts. Each invocation remains part of the caller's declared stage; reuse does not authorize hidden routing.
37. **Local lifetime.** A background ark service owns scheduling, event ingestion, and recovery; CLI and dashboard are clients. Closing a client or optional terminal multiplexer does not end the factory. Local machine sleep still pauses execution. OS startup integration is optional.
38. **Recovery.** Automatically reconcile and recover known-safe work after interruption. Inspect recorded jobs, resource leases, and forge operations before resuming. Reattach known-running jobs; resume safely stopped work from validated checkpoints with bounded retries. Ambiguous ownership or unknown external outcomes require human intervention; never start a second writer blindly.
39. **Missing cost telemetry.** Unknown cost does not block execution by default. Bound attempts, concurrency, and stage execution time; distinguish observed/reported cost, estimates with a pricing basis, and unknown cost. Environments may require stricter visibility. Ark must not claim an enforceable monetary cap without the necessary data/control.
40. **Pilot surface.** One service in the pilot environment's product platform repo. The pilot ticket (a historical change adding artifact-existence validation on registration) is a possible historical source for a real pilot ticket, not a required golden eval case. Live suitability is not yet verified.
42. **Factory evals removed.** No golden-ticket benchmarks, seeded-defect campaigns, hidden holdouts, skill/prompt/model eval suites, profile qualification, baseline promotion, external eval adapter, or eval dashboard. Ordinary ark software tests, adapter contract checks, deterministic product acceptance verification, and fail-before/pass-after defect proof remain in scope.
43. **Sandbox backend.** Box-first macOS pilot, with pinned binary version/digest and policy/configuration hashes. Claude Code, OMP, enterprise auth, protected-file access, build tooling, and cancellation require actual integration smoke before adoption. No uncontained fallback. Box is role-job isolation, not the orchestrator or an evidence authority; Compose/emulator remain verification-service capabilities. Other host platforms require a different backend. Box's short private state paths may live outside environment run folders to satisfy its socket-path limit.
44. **Isolation parked for Phases 0–1 (revises 12 and 43 for those phases).** Roles run directly on the engineer's machine as their user, inside per-ticket worktrees. No Box or other sandbox. Separation rules are enforced by detection, not prevention: the service hashes locked acceptance inputs and checks diff paths against `allowed_paths` after every attempt and rejects violations. Box remains the intended backend once isolation is reintroduced. Disclose "unsandboxed" in the run manifest.
45. **Ark is a project-agnostic plugin stack (public).** Ark is to products what pstack is to engineers: an installable stack of harness plugins (skills, role agents, commands) built over one core CLI, and that core spawns the local service and dashboard. The ark repo is public and contains no product material. Each product's agentic environment holds its `ark/` config and any product-specific findings (for example the pilot's Phase 0 findings and pilot ticket details). See design-spec §3 "Packaging".

## Implementation prerequisites and remaining delivery work

These are explicit prerequisites or specification work, not silently selected runtime settings:

- Identify approved enterprise inference endpoints/authentication and exercise both initial harnesses through Box.
- Resolve pinned runtime images/dependencies, isolated startup/seed/health/teardown tasks, and the concrete pilot-service ticket; do not reuse the engineer's live development stack for clean QE.
- Set project evidence retention/access policy and establish whether/how QMS records must be exported to an approved institutional record system. GitLab bundle storage alone does not establish regulatory compliance.
- Define the adapter and stage schemas, retry/timeout defaults, cancellation/reconciliation protocol, and artifact/rendering interfaces in the consolidated spec.
- Specify the source-based skill extraction and phased delivery. Factory evals are excluded; ordinary software and security/integration checks remain.
- Remote notifications, additional sandbox host platforms, Jira synchronization details, and approved ephemeral-deployment tasks belong to later explicitly scoped phases.
- Confirm shared understanding before implementation. No runnable ark engine or Box integration has been built or exercised in this interview.
