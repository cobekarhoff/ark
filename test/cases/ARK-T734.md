## Objective

Prove the orca reader pass adds no more than 150 ms to the hub's loop lag on a large Orca, and still returns the same snapshot (ARK-606/AC1). The rule is relative, not a plain 200 ms: the same hub with the same 100-run Ark home runs a control phase (no orca load), then the large pass, back to back, so the cost of the Ark, resources and usage readers of that home and the load of the host are in both lags and cancel. Both Orca reads that scale with the open runs, the pass (`readOrca`) and the conversation's directory read (`readDirectory`, which the 200 inbox messages send to the workers of every run), run in `hub/orca-worker.ts`: with the directory read on the loop, the large pass added 174, 1112 and 2012 ms in 3 of 6 runs at a host load of 50 to 224 (the other three added 90, 57 and 0 ms), and the round-4 `ark test --quick` failed ARK-T734 twice (added 162 and 285 ms) (`relative-rule.md`). A lag that remains at a host load of 190 or more is a hub process that the host starves, or `compose()` and Ark-reader cost, a separate cause that this case does not judge; the 200 ms limit of ARK-T699 is unchanged and is owned by that case. Expected: When the fake `orca` answers the reads of one `readOrca` pass with many open runs, many workers for each and a full inbox, the system shall keep the hub's largest measured loop lag, over the whole pass and the compose and publish it triggers, at most 150 ms above the largest lag of a control phase on the same hub, and the snapshot shall hold the agents and waits the fixture names, in the order Orca lists them.

Question 1: the loop lag of a large pass (the contract of ARK-533, now for the orca source) and the content of the snapshot after it. Question 2: the stall of the two failing captures of ARK-T699 (lag 277 ms and 318 ms, windows ending within 6 ms of the orca pass end, host load 19 to 37); a fix that yields or moves work but changes the order or count of `agents` and `waits`. Question 3: ARK-T699 has a fake `orca` that answers at once, 40 open runs and empty worker lists; it can fail on this stall only by luck on a loaded host, and never shows which part holds the loop. ARK-T700 owns what the lag field means; ARK-T730 owns the window message. This case is the only owner of "a large orca pass does not hold the loop". ARK-T395 and ARK-T320 own the shape of one agent; this case owns the count and the order across a large pass. Question 4: no hook; the test starts the real hub and reads `/api/health`, `/events` and `/api/snapshot`.

The cause is not proven (evaluation.md): the parse and map work of `readOrca`, the burst of `Bun.spawn` calls in one tick (two per open run: about 400 at 200 open runs), and the `compose()` plus `JSON.stringify` of `publish()` right after the pass are all candidates. The fixture therefore scales every dimension at once, so it is red whichever part holds the loop, and the validator proves the cause by the base runs in Preconditions (`results/evidence/ARK-T734/base/cause.md`: the spawn burst).

The control phase of the steps holds none of the three candidates: it leaves only Master Chief's Orca run in `orca.runs`, so the pass makes about four calls (`run-list`, `terminal list`, `inbox`, Master Chief's `worker-list`) and no per-run call. The one large answer in it is the full `orca.inbox`: `readOrca` parses it once and, with no Orca run for an open run, never reaches the per-run `pending` filter (hub/sources.ts), so it is one small parse (200 messages). The open runs' Orca runs and the workers enter at the switch, so a fix that bounds the per-run spawns cannot turn the control green or red. The inbox is in place from step 1 on purpose: a pass already in flight at the switch cannot read the new `orca.runs` together with an old, empty `orca.inbox`, because the inbox never changes at the switch and `orca.runs` is renamed last.

Where it lives: a new test in `test/hub-stall.test.ts`, beside ARK-T699 (it reuses `startHub`, the `/events` page helper and the health probe of the test support module `test/hub-stall-support.ts`, and `windowMessage` of `test/hub-stall-window.ts`).

## Waiting rule (test/wallclock.test.ts, ARK-T126)

The test holds no `setTimeout(`, `Bun.sleep(`, `waitForTimeout(` or `.toBeLessThan(<3 or more digits>)`, and the guard's allowance cannot be raised. Every wait is an event: a poll is a loop of health requests that ends when a source's `ended_at` advances (the requests are the wait), a read of the `/events` stream, or a process exit. The 150 ms the pass may add is the named constant `orcaLagAddedLimitMilliseconds`, compared in a boolean assert and never raised; the 200 ms `lagLimitMilliseconds` stays for ARK-T699 only. The validator runs `bun test test/wallclock.test.ts` before it finishes.

## Steps

1. Write the home, `orca.terminals`, the full `orca.inbox`, and an `orca.runs` that holds only Master Chief's Orca run (the open runs have no Orca run yet), and leave `orca.workers`, `orca.tasks` absent (the control: the orca pass makes its four calls and parses one 200-message inbox). The full `orca.runs`, with every open run's Orca run, is not written in this step: step 4 writes it to `orca.runs.next` and renames it over `orca.runs`. Start the hub, open `GET /events` and hold it, read its port.
2. Poll `GET /api/health` until the `orca` source's `ended_at` has advanced twice. Keep every answer as a probe (its time `performance.now() - start`, `lag_ms`, every source's `last_ms` and `ended_at`) and read `hub.output()` after each, stamping each new line with that probe's time, as ARK-T699 does. `healthProber(hub)` reads `Date.now()` and `performance.now()` together as `startEpoch` and `start`, after the hub started and the page opened; the probes and the window message use that one pair.
3. Control: keep the largest lag so far as `controlLag`, and the number of probes so far. It is what the home alone (the open runs, the Ark reader on that many runs, the other sources, the four orca calls and one inbox parse) and the host cost, with the cold first read included; step 6 judges only what the large pass adds over it. The test asserts nothing on `controlLag`, so a loaded host cannot fail the control alone. The per-run spawns and the large worker answers are not in this phase, so any fix of them leaves the control as it is.
4. Switch to the load: rename `orca.workers` and `orca.tasks` into place, then rename the full `orca.runs` over the Master-Chief-only file last. Every per-run call of a pass starts after its `run-list` resolves, so a pass that read the full `orca.runs` finds the workers and tasks in place; a pass that read the old `orca.runs` makes no per-run call and holds no Orca agents of an open run. Wait on the `/events` stream for a push in which an open run has its Orca agents (the first publish of a large pass) and keep that push's snapshot as `first`. Then poll health until the `orca` `ended_at` has advanced twice more (the large pass ended, its publish ran, and one more full pass ran after it), keeping every probe and stamped output line as in step 2. Read one more health answer after the last push of the stream, so the sample of the publish that follows the last pass end is inside the window.
5. Read `GET /api/snapshot` as `last`. Build the expected agents and waits of each open run from the fixture alone, by the rules of `agentsOf` and `readOrca` written out in the test (never by calling hub code): the agents in order (Master Chief, the run lead, then each worker in the order of `orca.workers`, with role, step, title, terminal and presence), and the waits in the order of `orca.inbox`, each with its step and `since`. Compare `first` and `last` with it, for every open run. Assert `sources.orca.ok` is true in `last`.
6. Build the message with `windowMessage` from every kept probe, every stamped line and `startEpoch`, on every run, put `ARK-T734` in front of it (the helper's own label reads `ARK-T699`). Take `largeLag`, the largest `lag_ms` of the probes from the switch on (the health lag reads the last 60 s, so these probes also see the control's spikes). Assert `largeLag <= controlLag + orcaLagAddedLimitMilliseconds` as a boolean; its failure message holds `controlLag`, `largeLag`, the added lag, the limit and the window message.
7. Stop the hub with SIGTERM and await its exit.

The snapshot assert (step 5) runs before the lag assert (step 6), so a fix that goes green on lag by dropping or reordering data fails on the snapshot with its own message, and the base run shows only the lag failure.

## Expected results

- Step 3: `controlLag` is read; no limit applies to it.
- Step 4: a push that holds the Orca agents of an open run arrives; the `orca` end time advances twice more; the answer after the last push exists.
- Step 5: in `first` (the first large pass) and in `last` (a later large pass) the agents of every open run equal the fixture's expected list (count, order, role, step, title, terminal, presence) and the waits equal the expected waits in order; the run with no Orca run has no Orca agents and no waits and the run with no worker has only Master Chief and its run lead; a run lead is present only for a connected terminal; `sources.orca.ok` is true in `last`. The fix returns the same snapshot for the same Orca answer on every pass.
- Step 6: `largeLag` is at most `controlLag` + 150 ms. At base this fails when the pass adds more than 150 ms; the message names `orca` with its last pass time and the stamped hub lines, or no hub line. The lag of the compose and publish after the pass end is included, because the 100 ms timer sample of the publish falls inside the probes of step 4.
- Red on unfixed code: step 6 fails with an added lag over 150 ms (base: `results/evidence/ARK-T734/relative-rule.md`; the evidence of ARK-T699: 277 and 318 ms at load 19 to 37). Step 5 passes at base. The deletions that must turn it red: the unfixed `readOrca` (the lag); a fix that yields in `readOrca` but leaves `compose()` and `JSON.stringify` of `publish()` unyielded when the cause is the publish (the lag, from the window that ends at the push); a fix that drops a run, sorts the workers or merges waits (step 5).
