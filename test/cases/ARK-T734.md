## Objective

Prove the orca reader pass never holds the hub's loop over 200 ms on a large Orca, and still returns the same snapshot (ARK-606/AC1). Expected: When the fake `orca` answers the reads of one `readOrca` pass with many open runs, many workers for each and a full inbox, the system shall keep the hub's measured loop lag at most 200 ms for the whole pass and for the compose and publish it triggers, and the snapshot shall hold the agents and waits the fixture names, in the order Orca lists them.

Question 1: the loop lag of a large pass (the contract of ARK-533, now for the orca source) and the content of the snapshot after it. Question 2: the stall of the two failing captures of ARK-T699 (lag 277 ms and 318 ms, windows ending within 6 ms of the orca pass end, host load 19 to 37); a fix that yields or moves work but changes the order or count of `agents` and `waits`. Question 3: ARK-T699 has a fake `orca` that answers at once, 40 open runs and empty worker lists; it can fail on this stall only by luck on a loaded host, and never shows which part holds the loop. ARK-T700 owns what the lag field means; ARK-T730 owns the window message. This case is the only owner of "a large orca pass does not hold the loop". ARK-T395 and ARK-T320 own the shape of one agent; this case owns the count and the order across a large pass. Question 4: no hook; the test starts the real hub and reads `/api/health`, `/events` and `/api/snapshot`.

The cause is not proven (evaluation.md): the parse and map work of `readOrca`, the burst of about 85 `Bun.spawn` calls in one tick (two per open run), and the `compose()` plus `JSON.stringify` of `publish()` right after the pass are all candidates. The fixture therefore scales every dimension at once, so it is red whichever part holds the loop, and the validator proves the cause by the base runs in Preconditions.

The control phase of the steps holds none of the three candidates: it leaves only Master Chief's Orca run in `orca.runs`, so the pass makes about four calls (`run-list`, `terminal list`, `inbox`, Master Chief's `worker-list`) and no per-run call. The open runs, the workers and the unread messages enter at the switch, so a fix that bounds the per-run spawns cannot turn the control green or red.

Where it lives: a new test in `test/hub-stall.test.ts`, beside ARK-T699 (it reuses `startHub`, the `/events` page helper, the health probe and `windowMessage` of `test/hub-stall-window.ts`).

## Waiting rule (test/wallclock.test.ts, ARK-T126)

The test holds no `setTimeout(`, `Bun.sleep(`, `waitForTimeout(` or `.toBeLessThan(<3 or more digits>)`, and the guard's allowance cannot be raised. Every wait is an event: a poll is a loop of health requests that ends when a source's `ended_at` advances (the requests are the wait), a read of the `/events` stream, or a process exit. The 200 ms limit is the named constant `lagLimitMilliseconds` already in the file, compared with `toBeLessThanOrEqual` or a boolean, and never raised. The validator runs `bun test test/wallclock.test.ts` before it finishes.

## Preconditions

- Temp `ARK_HOME`, session roots and fake tools on `PATH` from the `stage()` of `test/hub-stall.test.ts`, `ARK_READER_TIMEOUT_MS=30000`, `ARK_PS` and `ARK_LSOF` fakes as there, and no session files (the usage reader reads nothing, so a lag over 200 ms is not the usage source).
- The fixture is opt-in. It is a set of state files that only this test writes: `orca.workers`, `orca.tasks`, `orca.workers.<orca run id>`, and the existing `orca.runs`, `orca.inbox` and `orca.terminals`. The fake `orca` of `stage()` (local to `test/hub-stall.test.ts`) answers `worker-list --run <orca run id>` from `orca.workers.<orca run id>` when that file exists, else from `orca.workers`, and `task-list` from `orca.tasks`, when the file exists, and with the empty list as now when it does not, so every other caller of this `stage()` (ARK-T699, ARK-T700, ARK-T701, ARK-T702, ARK-T703) sees the same answers as now. The shared fake `orca` of `test/hub-fixtures.ts` is never edited (its callers: test/hub.test.ts, test/hub-idle.test.ts, test/companions.test.ts, test/pw/helpers.ts and the cases ARK-T125, T192, T23, T24, T271, T290, T309, T311, T319, T670, T76, T78). The test writes each large file to a temp name and renames it, so a read never sees half a file.
- The home: `openRunCount` runs in `building` written with `writeRun` (project `p`), each with an Orca run (objective `Ark run <run>`, a `coordinator_handle` that `orca.terminals` lists as connected) in the full `orca.runs`, plus Master Chief's run (`Master Chief: p tickets`, its terminal connected). Master Chief's run is the only run in `orca.runs` until the switch of step 4, and has its own `orca.workers.<chief orca run id>` with the empty list (the shared `orca.workers` is for the open runs). The fake ignores `--limit` and `--cursor`, so every `worker-list` of an open run answers the whole `orca.workers` at once (a real page holds at most 100 rows, so the file is larger than live data on purpose). `orca.workers` holds `workerCount` workers: each with a `dispatchId`, `terminal`, `agentTerminalHandle`, `taskId`, `state` and a `projection` with liveness and provider (as the conversation fixture of test/hub.test.ts); a third of them `released` or dead (so presence `ended`), the rest `live` or `running`. `orca.tasks` holds a task for each worker, with a title naming a step (`<role> step <id>` as `stepTask` reads it). The full `orca.inbox` holds 200 unread messages (the `inbox --limit 200` size) of type `question` or `escalation`, addressed to `run:<orca run id>` of the open runs in turn and sent from the handles of workers in the list, so the `pending` filter of `readOrca` scans the whole worker list for every message.
- Edge runs inside the fixture: the last open run has no Orca run in `orca.runs` (the pass skips it: no Orca agents, no waits), and the one before it has an Orca run whose `worker-list` answers no worker (the fake answers the empty list for its run id from an `orca.workers.<orca run id>` file, while the shared file answers every other open run). Each is the first or last item of a split pass.
- Master Chief's `orca.workers.<chief orca run id>` list stays empty in both phases, so the run lead of every open run is present through its connected terminal (the case for a run lead listed only by Master Chief's `worker-list` is ARK-T735).
- Size: `openRunCount`, `workerCount` and the inbox are set by the validator so that the unfixed hub's pass measures over 200 ms, starting from 120 open runs (240 `Bun.spawn` calls in one tick), 500 workers for each run, and 200 messages, and raised until it does. Building the files and runs takes under 15 s in the test process with sync writes.
- Control and cause evidence from the validator (a one-time probe, kept in `results/evidence/ARK-T734/base/`, never a second test; time box 30 minutes): the same hub at base run three times with one dimension large and the other two small (many runs and no workers; few runs and many workers; few runs and a full inbox over many workers). For each: the largest lag, and the window message that names the source and the pass time. To name the blocker, the validator also profiles the hub during the fixture's large pass with `bun --cpu-prof` in a second process (the hub started as `bun --cpu-prof hub/main.ts --port 0`, the profile file kept beside the evidence), and reads which function holds the loop: the `readOrca` parse and map, the `Bun.spawn` burst, or the `compose()` and `JSON.stringify` of `publish()`. Together they name which of the three holds the loop at base. A dimension that alone does not pass 200 ms stays in the fixture as part of the sum. If no sum reaches 200 ms at base, the validator records that and the largest lag reached, and escalates: it never lowers the limit and never adds a delay to the fake.
- A real `bun hub/main.ts --port 0` with `ARK_HUB_INTERVAL_MS=2000` (the interval ARK-T703 uses) and a held `/events` stream (the lag is `null` with no page).
- The test sets its own timeout of 90 s.

## Steps

1. Write the home, `orca.terminals`, and an `orca.runs` that holds only Master Chief's Orca run (the open runs have no Orca run yet), and leave `orca.workers`, `orca.tasks` absent and `orca.inbox` empty (the control: the orca pass makes its four calls and reads nothing large). Write the full `orca.runs`, with every open run's Orca run, and the full `orca.inbox` under temp names for step 4. Start the hub, open `GET /events` and hold it, read its port.
2. Poll `GET /api/health` until the `orca` source's `ended_at` has advanced twice. Keep every answer as a probe (its time `performance.now() - soakStart`, `lag_ms`, every source's `last_ms` and `ended_at`) and read `hub.output()` after each, stamping each new line with that probe's time, as ARK-T699 does. Read `Date.now()` and `performance.now()` together as `soakStartEpoch` and `soakStart` before step 1.
3. Control: assert the largest lag so far is at most `lagLimitMilliseconds`. This fails first if the home alone (the open runs, the Ark reader on that many runs, the other sources, the four orca calls) holds the loop, so a later red is the orca pass of the fixture and not the home. The per-run spawns and the large answers are not in this phase, so any fix of them leaves the control as it is.
4. Switch to the load: rename `orca.workers`, `orca.tasks`, the full `orca.runs` and the full `orca.inbox` into place. Wait on the `/events` stream for a push in which an open run has its Orca agents (the first publish of a large pass) and keep that push's snapshot as `first`. Then poll health until the `orca` `ended_at` has advanced twice more (the large pass ended, its publish ran, and one more full pass ran after it), keeping every probe and stamped output line as in step 2. Read one more health answer after the last push of the stream, so the sample of the publish that follows the last pass end is inside the window.
5. Read `GET /api/snapshot` as `last`. Build the expected agents and waits of each open run from the fixture alone, by the rules of `agentsOf` and `readOrca` written out in the test (never by calling hub code): the agents in order (Master Chief, the run lead, then each worker in the order of `orca.workers`, with role, step, title, terminal and presence), and the waits in the order of `orca.inbox`, each with its step and `since`. Compare `first` and `last` with it, for every open run. Assert `sources.orca.ok` is true in `last`.
6. Build the message with `windowMessage` from every kept probe, every stamped line and `soakStartEpoch`, on every run, and use it as the failure message of the lag assert. Assert the largest `lag_ms` of all probes since the switch is at most `lagLimitMilliseconds`.
7. Stop the hub with SIGTERM and await its exit.

The snapshot assert (step 5) runs before the lag assert (step 6), so a fix that goes green on lag by dropping or reordering data fails on the snapshot with its own message, and the base run shows only the lag failure.

## Expected results

- Step 3: the control lag is at most 200 ms (the home is not the stall).
- Step 4: a push that holds the Orca agents of an open run arrives; the `orca` end time advances twice more; the answer after the last push exists.
- Step 5: in `first` (the first large pass) and in `last` (a later large pass) the agents of every open run equal the fixture's expected list (count, order, role, step, title, terminal, presence) and the waits equal the expected waits in order; the run with no Orca run has no Orca agents and no waits and the run with no worker has only Master Chief and its run lead; a run lead is present only for a connected terminal; `sources.orca.ok` is true in `last`. The fix returns the same snapshot for the same Orca answer on every pass.
- Step 6: the largest lag is at most 200 ms. At base this fails on a pass that holds the loop over 200 ms; the message names `orca` with its last pass time and the stamped hub lines, or no hub line. The lag of the compose and publish after the pass end is included, because the 100 ms timer sample of the publish falls inside the probes of step 4.
- Red on unfixed code: step 6 fails with a lag over 200 ms (the evidence of ARK-T699: 277 and 318 ms at load 19 to 37). Steps 3 and 5 pass at base. The deletions that must turn it red: the unfixed `readOrca` (the lag); a fix that yields in `readOrca` but leaves `compose()` and `JSON.stringify` of `publish()` unyielded when the cause is the publish (the lag, from the window that ends at the push); a fix that drops a run, sorts the workers or merges waits (step 5).
