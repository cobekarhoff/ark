## Objective

Prove the hub's readers of a large Ark home add no more than 150 ms to the hub's loop lag, and the pass still returns the same snapshot (ARK-613/AC1). The rule is relative, as in ARK-T734: the same hub runs a control phase on a near-empty home, then the large project is renamed into place and the hub reads it, back to back, so the host's load, the orca, usage and provider sources and the fixed fake answers are in both lags and cancel. What is left is the cost of the home: the Ark reader's cold read of every run and ticket, the watcher sync, the queue and unread reads of the new project, the resources writes of its open runs, and the compose and publish of the larger snapshot. The cause is not named here (the ticket forbids a guess before the profile); the fixture has the real shape on every dimension, so the case is red whichever of them holds the loop.

Question 1: the loop lag of one full snapshot pass over a home of the real size (the contract of ARK-533 and ARK-606, now for the Ark home), and the content of the snapshot after it. Question 2: the windows of the ARK-606 retro over 200 ms at load 55 and above that name `ark`, `queue`, `chiefUnread`, `resources`, `usage` and `providerLimits`, and compose() up to 87 ms plus JSON.stringify up to 60 ms; a fix that yields, chunks or moves this work into a worker and with it drops, reorders or caches stale runs, tickets, costs or role times. Question 3: ARK-T699's `largeHome()` writes 250 plain runs with `writeRun` (4 or 5 events each, no plan.yml, a `metrics.json` of one cost field) and one ticket, so its cold read is a fraction of the real one and it fails only by luck on a loaded host; ARK-T734 holds the home fixed at 100 plain runs and changes only Orca's answers, so the home's cost cancels in its control. This case is the only owner of "a large Ark home does not hold the loop". ARK-T700 owns what the lag field means; ARK-T730 owns the window message; ARK-T734 owns the orca pass. Question 4: no hook; the hub runs as `bun hub/main.ts --port 0`, and the fixture is files in a temp `ARK_HOME` and fake tools on `PATH`.

Where it lives: a new file, `test/hub-home-lag.test.ts`, not `test/hub-stall.test.ts` (that file takes 239 s in `test/timings.json`; a third large-home test there adds to the longest file of the `cli` suite). The helpers it needs from `test/hub-stall.test.ts` (`stage()` with its fake tools, `startHub`, the `/events` page helper, the health probe and its prober) move into one test support module, `test/hub-stall-support.ts`, that both files import, with no `test(` in it, rather than a copy (rules/test-audit.md: extend fixtures, never copy setup). The move changes nothing that ARK-T699 to ARK-T735 do. The prober gets the sources to wait on as an argument (`orca` alone for ARK-T734 and ARK-T735) and the case id of its message. The run folders come from `writeRun` of `test/hub-fixtures.ts`, extended with optional fields (a verbatim `plan.yml` text, as `metricsText` is for `metrics.json`, and extra events) that no other caller sets. The shared fake `orca` of `test/hub-fixtures.ts` is never edited. `windowMessage` comes from `test/hub-stall-window.ts`, unchanged.

## Waiting rule (test/wallclock.test.ts, ARK-T126)

The test holds no `setTimeout(`, `Bun.sleep(`, `waitForTimeout(` or `.toBeLessThan(<3 or more digits>)`, and the guard's allowance cannot be raised. Every wait is an event: a poll is a loop of health requests that ends when the named sources' `ended_at` advance (the requests are the wait), a read of the `/events` stream, or a process exit. The 150 ms the large pass may add is a named constant, `homeLagAddedLimitMilliseconds`, compared in a boolean assert and never raised; `lagLimitMilliseconds` (200, ARK-T699) and `orcaLagAddedLimitMilliseconds` (150, ARK-T734) are not touched. The validator runs `bun test test/wallclock.test.ts` before it finishes. That guard scans only files that end in `.test.ts` or `.pw.ts` (`sources()` of test/wallclock.test.ts), so it scans `test/hub-home-lag.test.ts` but not the support module `test/hub-stall-support.ts`, where `stage()`, `startHub` and the prober live. The support module is outside the guard: the validator greps it with the guard's four patterns (`rg -n 'waitForTimeout\(|Bun\.sleep\(|setTimeout\(|\.toBeLessThan\(\s*\d[\d_]{2,}\s*\)' test/hub-stall-support.ts`) and records no hit (on 2026-11-20 the same grep of `test/hub-stall.test.ts`, where those helpers live now, printed no hit; the `sleep` of the fake shell scripts is not one of the patterns).

## Steps

1. Write the control home, the fake answers and the opt-in files, and build `big` in `$ARK_HOME/staging/big`. Start the hub, open `GET /events` and hold it, start the prober (it reads `Date.now()` and `performance.now()` together as `startEpoch` and `start`).
2. Poll `GET /api/health` until each source that reads the home (`ark`, `usage`, `evidence`, `queue`, `chiefUnread`, `resources`) has ended two passes. Keep every answer as a probe (its time `performance.now() - start`, `lag_ms`, every source's `last_ms` and `ended_at`) and read `hub.output()` after each, stamping each new line with that probe's time, as ARK-T734 does.
3. Control: keep the largest lag so far as `controlLag` and the number of probes so far. It is what the near-empty home, the fixed fake answers and the host cost, with the cold first read included. The test asserts nothing on `controlLag`, so a loaded host cannot fail the control alone. Read `GET /api/snapshot` and assert it holds no run and no ticket of `big` (the switch has not happened yet).
4. Switch: rename `$ARK_HOME/staging/big` to `$ARK_HOME/projects/big` with one rename, and keep the time as `switchedAt`. One full pass is defined here: no watcher sees `$ARK_HOME/projects`, so the next `ark` tick (2 s) reads the whole project in one pass, cold, as a hub start on the real home does, and no pass reads it in part. Probe health and read the `/events` stream until a push holds a run of `big`; keep that push's snapshot as `first`. Then poll until each source of step 2 has ended two more passes after that push (the queue, unread, resources and evidence reads of `big` and one warm Ark pass ran), then probe once more (the sample of the last publish), keeping every probe and stamped line.
5. Read `GET /api/snapshot` as `last`. Build the expected values from the fixture alone (never by calling hub code). Compare `first` and `last` with them on the surfaces of the Ark pass (`runs`, `gates`, `tickets`, `ticket_runs`, `roadmap`, `role_times`): `first` is the publish of the `ark` pass that read `big`, and these surfaces all come from that pass. Compare `queues` and `chief_unread` on `last` only: the `queue` and `chiefUnread` sources call `listProjects()` in passes of their own, and compose sends their last reads, so the `ark` pass can publish `first` before either has seen `big`; by `last` each has ended two passes after `first` (step 4).
   - `runs`: the open runs of both projects (`p`'s run and the 4 open runs of `big`), newest run name first (numeric order), each with project, ticket id, phase, plan step ids and statuses (null for the run whose plan does not parse), `progress.steps_done` and `steps_total`, and merge request urls.
   - `gates`: one gate, the plan gate of the `planning` run.
   - `tickets`: every readable and unreadable ticket of `big` in file-name order (id, title, status; `unreadable` for the broken one), and none of `p`.
   - `ticket_runs`: one entry for each ticket of a run, with its newest run and phase; for a closed run `cost_usd` is the total of its `metrics.json`, and null for the 6 closed runs with none; `all` holds every run of the ticket, newest first, with phase, outcome and cost. The cost of an open run is not compared (it comes from session files, which the fixture has none of; the usage cases own it).
   - `roadmap`: for `big`, the milestones and the ticket ids under each in the order of the fixture's `ROADMAP.md`; for `p`, the no-roadmap value of a `local` project.
   - `role_times`: for each role, median and p90 equal the fixture's one duration for that role, and the count equals its number of windows in the closed runs.
   - `queues` (on `last`): for `big`, `open` equals its 4 open runs and `tasks` equals each task of `orca.tasks` in order with status `ready`, then each task of `orca.tasks.pending` in order with status `pending`, each with the ticket id of its title; for `p`, an `unavailable` entry that names the missing `Master Chief: p tickets` run.
   - `chief_unread` (on `last`): for `big`, the count of unread messages of `orca.chief-inbox` and the oldest `created_at` of them; for `p`, `none`.
   - In `last`, `sources.ark.ok`, `sources.chiefUnread.ok` and `sources.resources.ok` are true, and `sources.queue.ok` is false: the queue source reads not ok when any project's queue is `unavailable` (hub/snapshot.ts, the `queue` reader), and `p` has no Master Chief run, at base and at head. The entry of `big` in `queues` is what proves its queue read; a failed read of `big` shows as an `unavailable` entry, not as its tasks.
   - Not compared, with the reason: the values of `resources` (live host readings) and `provider_limits` (the fake `omp` answers the same in both phases; no reader of the home makes them).
6. The files the hub writes: each open run of `big` has `results/resources.json` with `sampled_until` at or after `switchedAt`, and no closed run of `big` has one.
7. Build the message with `windowMessage` from every kept probe, every stamped line and `startEpoch`, on every run, with `ARK-T751` in front of it. Take `largeLag`, the largest `lag_ms` of the probes from the switch on (the health lag reads the last 60 s, so these probes also see the control's spikes). Assert `largeLag <= controlLag + homeLagAddedLimitMilliseconds` as a boolean; its failure message holds `controlLag`, `largeLag`, the added lag, the limit and the window message.
8. Stop the hub with SIGTERM and await its exit.

The snapshot and file asserts (steps 5 and 6) run before the lag assert (step 7), so a fix that turns the lag green by dropping or reordering data fails with its own message, and the base run shows only the lag failure.

## Expected results

- Step 3: `controlLag` is read; no limit applies to it. The control snapshot holds nothing of `big`.
- Step 4: a push that holds the runs of `big` arrives; each source of step 2 ends two more passes.
- Step 5: `first` (the first push of the large pass) and `last` (after a warm pass) each equal the expected values on every surface of the Ark pass: the run folders with no events are not runs, the run with the broken plan has a null plan, the closed runs with no `metrics.json` have a null cost, never 0, and the broken ticket reads `unreadable`. The fix returns the same snapshot for the same home on the cold and the warm pass, and never pushes the home in part. `last` holds the queue of `big` (ready then pending, no task twice), the `unavailable` queue of `p`, the unread count of `big` and `none` for `p`; `sources.queue.ok` is false, from the `unavailable` entry of `p` alone.
- Step 6: the resources file of every open run of `big` is written after the switch; no closed run gets one.
- Step 7: `largeLag` is at most `controlLag` + 150 ms. At base this fails with an added lag over 150 ms; the message names the passes and hub lines of the window of the largest lag (a name in a window is not proof that the pass held the loop; the profile names the cause).
- Red on unfixed code: step 7 fails at base in 3 of 3 runs at the scale of Preconditions (the record in `results/ARK-T751-scale.md`); steps 5 and 6 pass at base (the surfaces compared on `first` all come from the `ark` pass that `first` publishes, and the queue and unread values are compared on `last`, after each of those sources ended two passes over `big`). The changes that must turn it red at head: removing the fix (step 7); a fix that yields in the Ark reader but leaves compose() and JSON.stringify of publish() whole when the profile names them (step 7, from the window that ends at the push); a pass or publish that pushes the runs or tickets of `big` in parts (step 5, `first`); a worker that loses the ticket files, the roadmap or the closed runs' costs (step 5); a cost cache that shows a closed run with no `metrics.json` as 0 (step 5); a queue or unread fix that drops the pending tasks of `big`, reorders its tasks or reads its queue as `unavailable` (step 5, `last`); a resources fix that skips the per-run write (step 6).
