## Objective

Prove `ark merge-request check <run> --stage head|step|final [--step <id>] [--summary <text>]` prints the problems that the stage owns, exits 1 when one exists and 0 when none, and changes no file, event or remote. A stage never prints a problem of a later stage, and a later stage prints everything of an earlier one. The text is the text of `ark merge-request open`: an evidence problem is one line each (open carries them under one header line), and the AC-string problems are one joined line, as open throws them today.

## Preconditions

- Fixture rule (order matters; ARK-405 review 4): `ark run start` fixes the run's criteria (`cli/run.ts:99`, `cli/events.ts:190`), and `ark gate record <run> manual AC2 ok` refuses an AC that is not in that list (`cli/gate.ts:68-69`: `criterion FAKE-1/AC2 is not in the ticket`). A second `ark plan check` after an edit of `plan.yml` clears the approval and sends the phase back to `planning` (`cli/events.ts:230`, `:366`), after which open refuses with `cannot open merge requests while the run is in phase planning` (`cli/merge-request.ts:437-439`). So the ACs of the ticket, the plan steps and the `summary.changes` rows are written BEFORE `ark run start` and its `plan check`: `syncedRun` of `test/sync-base.test.ts` gets new options for them (for example `criteria`, `plan`, and `title` and `summary` for the ticket) and writes them where it now writes its one-AC ticket and its plan. After `syncedRun` returns the test never edits `plan.yml` or the criteria again, and never runs a second `plan check`. The only later edit of the ticket is the text of an AC in the run's `ticket.md` with the same ids (step 10; `criterionTexts` reads that file, `cli/merge-request.ts:59-72`). Gate answers, evidence files, commits and appended events are fine after the return.
- Base fixture: `syncedRun("feature", { verified: true, criteria, plan })` of `test/sync-base.test.ts` with those options: a git repo with a local bare `origin` on `main`, a run in the building phase with a worktree. Ticket `FAKE-1`; the ACs are `FAKE-1-AC1` (`method: test`, `verified_by: [FAKE-T1]`, text holds the two backticked strings `` `no-such-string-405` `` and `` `no-such-other-405` ``), `FAKE-1-AC2` (`method: analysis`) and `FAKE-1-AC3` (`method: demonstration`); they read as `FAKE-1/AC1` to `FAKE-1/AC3`. The plan has a `summary.changes` row for each AC, an implementer step `build` and a validator step `check` (needs `build`, same harness and model pair as an `ark.yml` role); both serve all three ACs; the `ark plan check` inside `syncedRun` passes and records `build` and `check` in `plan.checked`. After the return the test appends two events with `appendEvent` (a real `ark run step build start` would launch a worker): `step.started` with `{ step: "build", role: "implementer", repo: ".", round: 1 }` (the shape `runStep` writes, `cli/run.ts:513-518`; the `round` key is required, because `deriveState` takes `Math.max(round, data.round)`, `cli/events.ts:287`, and a missing `round` makes `state.round` `NaN`) and `step.finished` with `{ step: "build", outcome: "succeeded" }`. So the implementer has finished and no AC-string deferral applies (that rule is owned by ARK-T381). Evidence files are written by the test in `results/evidence/` of the run folder, not in the worktree.
- Problem fixture (the base fixture, no `ark test` run): no tracked file holds either string. `AC2` has no evidence file. `AC3.md` is malformed: it holds a non-empty `What the human did`, `Before` and `After` section but no `What the human saw` section and no `human: ok` line, so its reason is `missing section "What the human saw"`. The ticket has no `summary:` line (`writeTicket` writes none), so the default title `FAKE-1: Ticket FAKE-1` is short. The test holds a `--summary` text that makes `FAKE-1: <summary>` 73 characters long.
- Control fixture (the base fixture with every file well-formed, built in this order): a tracked file in the worktree holds both strings (committed); `AC2.md` is a well-formed analysis file (sections `Command`, `Output`, `Threshold` and `Result`, each with a `Base` and a `Head` label); `AC3.md` is a well-formed demonstration file (the four sections, a screenshot path under `Before` and `After`, no `human: ok` line); `AC2` and `AC3` are answered with `ark gate record <run> manual AC2 ok` and `... AC3 ok` (every non-test AC is a manual criterion; the gate adds `human: ok` to `AC3.md` and writes nothing for the analysis file); then `ark test <run>` exits 0. No commit follows the test, so no head moves.
- Passing fixture: the control fixture built without the `AC3` answer. `ark test <run>` still runs after the `AC2` answer; it exits 1 (`FAKE-1/AC3 is manual pending`, existing behaviour) and still writes `test.completed` with `passed: true`. `AC3.md` is well-formed but has no `human: ok` line.
- Long-title fixture (the shape of ticket 6 in ARK-T54): the title of a run is the `title` in the `run.started` event, which `ark run start` writes once from the ticket file (`cli/run.ts:94-97`, read back by `deriveState`, `cli/events.ts:189`); an edit of the run's `ticket.md` after the start does not change it, but the `summary:` line is read from the run's `ticket.md` each time (`ledger.ts:921-922`). So this run is one more `syncedRun` call with the options of the base fixture plus a long `title` (for example 70 characters, so `FAKE-1: <title>` is over 72) and a `summary` of the same length: `syncedRun` writes the ticket with `writeTicket` and that title (fourth argument, `project, id, criteria, title, kind`) and adds a `summary:` line to the frontmatter of that ticket file BEFORE `ark run start` (the fixture rule above). The rest is built as the control fixture does (the same ACs, plan, files and answers). Every file is well-formed and every AC string is tracked, so a title problem is the only possible problem. Both `buildTitle` candidates (the summary, then the title) are over 72 characters, so with no `--summary` there is no usable title.
- Step-5 variant fixture: one more `syncedRun` call whose `plan` option gives `check` only `FAKE-1-AC1` (the ticket still has the three ACs and the plan keeps a `summary.changes` row for each), and otherwise the problem fixture.
- Every fixture is its own `syncedRun` call, and each call runs `tempArkHome`, which resets `process.env.ARK_HOME` (`test/helpers.ts:19-23`). Before each `ark` command the test sets `ARK_HOME` back to the `ARK_HOME` of the fixture it works on, so no command reads another fixture's run folder. Every fixture has the fake host of `test/fixtures/merge-request` first on `PATH` (`useFakeHost()` of `test/sync-base.test.ts:264`), so `tokenOwner` never runs the real `gh api user`: the origin path of `syncedRun` holds `github.com` (`test/sync-base.test.ts:86`), so `hostOf` returns `github`.
- Before each `check` call the test records: the bytes of `events.ndjson`, `git status --porcelain` and a recursive listing with sizes of the run folder and the worktree, and `git ls-remote origin`.

## Steps

1. Run `ark merge-request check <run> --stage head` in the problem fixture. Assert exit 1 and that the output holds exactly one line for the AC strings: ``AC string in no tracked file at head: FAKE-1/AC1 `no-such-string-405`; FAKE-1/AC1 `no-such-other-405` `` (both strings in the one joined line of open's text; the AC is named by its canonical id), and one line `evidence malformed: AC3: missing section "What the human saw"`. Assert no line says `evidence missing` (the file of `AC2` is due later) and no title line (the default title is short).
2. Run the same with `--summary <73 characters>`. Assert exit 1 and a title line that names the 73 characters and the 72 allowed, with the title text, which is the text of `buildTitle` (`--summary makes a title of 73 characters, 72 allowed: <title>`). Assert the lines of step 1 are still there.
3. In the long-title fixture run `--stage head` with no `--summary`. Assert exit 1 and the line `ticket has no summary: pass --summary` (the branch of `buildTitle` where neither the ticket summary nor the ticket title fits; the only title problem that `ark test` can see). Run it with a short `--summary`: exit 0 and no output.
4. In the problem fixture run `--stage step --step check` (the validator serves `AC2` and `AC3`). Assert every line of step 1's output is present and a line `evidence missing: AC2 (analysis)` is added. Assert each evidence problem is on its own line, no line appears twice, and the AC-string problems are still the one joined line.
5. In a variant of the problem fixture whose plan gives `check` only `AC1`, run `--stage step --step check`. Assert no `evidence missing: AC2` line. Run `--stage step` without `--step`: the lines for `AC2` are back, because without a step the stage serves every AC.
6. In the problem fixture (no test result) run `--stage final`. Assert exit 1, every line of the step stage (run with no `--step`), and the line ``no test result yet: run `ark test` first``. Which later lines `final` adds while no test result exists is not pinned.
7. In the passing fixture: `--stage head` and `--stage step` exit 0 and print nothing (the `AC3` file lacks only `human: ok`, which neither stage checks; `AC2.md` exists). `--stage final` exits 1 and prints the line of `ark merge-request open` for the manual criterion, `manual criterion without ok: FAKE-1/AC3` (the canonical id that `manualCriteria` returns, `cli/ticket.ts:46`; one criterion, so the singular text; `AC2` is answered). The output may hold other final-stage lines (for example `evidence malformed: AC3: the last line is not "human: ok"`); only the manual line is pinned, and there is no `no test result` line.
8. In the control fixture run the three stages. Assert each exits 0 and prints no line.
9. Final evidence lines against open: in the control fixture delete `results/evidence/AC2.md` and remove the `What the human saw` section from `AC3.md` (its answer stays recorded). Run `--stage final`: exit 1 and the two lines `evidence missing: AC2 (analysis)` and `evidence malformed: AC3: missing section "What the human saw"` each on its own line. Run `ark merge-request open <run>`: it is refused with one message whose first line is `refused: evidence is not complete` and whose next lines are those two lines in the same order. Remote refs and `events.ndjson` are unchanged by the refusal.
10. AC string against open: in the control fixture (files restored) replace the text of `AC1` in the run's `ticket.md` with a text that holds two new backticked strings `` `absent-one-405` `` and `` `absent-two-405` `` that no tracked file holds. `--stage head` prints the one joined line ``AC string in no tracked file at head: FAKE-1/AC1 `absent-one-405`; FAKE-1/AC1 `absent-two-405` ``. `ark merge-request open <run>` is refused with an error text equal to that line byte for byte (no head moved, so the stale-head refusal does not come first).
11. After every `check` call above compare the record taken in preconditions: `events.ndjson` is byte-identical, the porcelain and the listings are equal, `git ls-remote origin` is equal.

## Expected results

- When a stage lists a problem, the system shall print it and exit 1; when none, it shall print nothing and exit 0.
- Each evidence problem shall be its own line; the AC-string problems shall be the one joined line that open throws.
- Stage `head` shall list an AC string in no tracked file, a title problem (`--summary` over 72 characters, or `ticket has no summary: pass --summary` when no summary and no ticket title fit), and the shape problem of each evidence file that exists, and shall list no missing file, no `human: ok` problem and no `reviewer:` problem.
- Stage `step` shall add `evidence missing` for the non-test ACs that the named step serves, and for every AC when no `--step` is given.
- Stage `final` shall add the other refusals of `assertShippable` (no test result, manual criterion without ok, evidence problems).
- The text of a problem shall be the text that `ark merge-request open` refuses with; open's evidence refusal stays one message headed `refused: evidence is not complete`.
- While it runs, the system shall write no event, no file and no ref.
