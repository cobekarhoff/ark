## Objective

Prove a `bun test` of the whole suite (no path argument, or a directory argument) started outside `ark test` takes its cores from `test_budget_cores` through the real ticket store, runs no test file until the cores are free, and keeps the ticket until its last file ends.

Expected: with the budget full, no file runs and one waiting line shows; after the holder ends, the run holds one ticket while a file is still running, and the ticket is gone after the run exits.

## Preconditions

- Temp `ARK_HOME` with project `demo` whose `ark.yml` sets `test_budget_cores: 3` and `workspace` to a scratch git repo.
- The scratch repo has the repo's `bunfig.toml` preload and four test files under `test/` (a fake suite): `a`, `b` and `c` each open the write end of a named pipe `alive-<name>` and keep it open (the case opened the read ends before the run; the descriptor closes when the file's worker exits), then append `process.pid` to a marker file `ran-<name>` and their working folder to the shared log `runs.log`; `gate` does the same with `alive-gate`, opens a named pipe (`gate`) for reading, appends its `process.pid` and working folder to `started-gate`, blocks reading the pipe until end-of-file, then appends its `process.pid` to `ran-gate`. The case holds a read-write descriptor of the `gate` pipe from the start and closes it to release the gate: a reader that opens a pipe before any writer stays blocked on macOS when a writer opens and closes first, so the case never opens a short-lived writer. The `ARK_FAKE_HOST` and PATH shims come from the outer preload, so memory admission does not hold the run. A worker's exit is the end-of-file of its `alive-*` pipes: no poll, no sleep.
- The environment of every `bun test` child the case starts is built, not inherited: the environment of the case minus the `ark test` marker (the name `run()` in `cli/test-run.ts` sets), `BUN_TEST_WORKER_ID`, `JEST_WORKER_ID`, `ARK_PROJECT` and `ARK_HOME`; then `ARK_HOME` is the temp folder, and `ARK_PROJECT` is set only in the row that says so. Reason: the case itself may run under `ark test` (the marker would make the child never wait) or under an outer `bun test --parallel` (the worker variables would make a serial child read the command line of its parent).
- The holder is a real child process: `openTestBudget("holder", 3, ...)` and `await budget.take(<cores>)` from `cli/test-lock.ts`, then it blocks reading its standard input until the case writes to it (the release). Its ticket pid is live.
- No sleeps: the case waits on events (a line read from the child's output, a marker file, process exit).
- A marker counts as written only when it holds a complete line: a file appends with create then write, so a marker file that exists and is still empty is not written yet, and neither a wait for it nor a read of its pid sees it. Without this rule a read of the pid gives no pid, the case takes a worker that also runs `gate` for another worker, and waits for end-of-file of a pipe that `gate` still holds (the Linux hang of ARK-527).

## Steps

1. Start the holder and wait until its ticket is running (3 of 3 cores).
2. Start `bun test --parallel=3` with no path in the scratch repo (cwd the workspace), as a detached child with no terminal. A serial row reads its output until the waiting-for-budget line shows. A `--parallel` row cannot: a worker's output reaches the pipe when its file ends (even over a pipe, with no channel to the coordinator), so the row waits until the bare run's ticket file exists in the store, which is the point where the run waits. Check that no `ran-*` marker and no `started-gate` exists and that the child is alive.
3. Read the ticket store: the bare run has one waiting ticket with label `bun test`, asking 3 cores, with the pid of the `bun test` process the case spawned (the coordinator, not a worker).
4. Run `ark chief state` against the same `ARK_HOME` and read the `## ark test budget` section.
5. Release the holder. Wait until `started-gate` exists. In a `--parallel` row also wait until every `ran-*` marker of `a`, `b` and `c` exists, read the pids in the markers and in `started-gate`, and for each file whose pid differs from the `gate` pid wait for end-of-file on its `alive-<name>` pipe (that worker has exited; the `gate` worker is still alive and still runs `gate`). When every pid equals the `gate` pid no worker ended, and the row checks the ticket only. In a serial row nothing else is waited for, because a serial run does not use name order and `gate` may run before `a`, `b` or `c`. Read the ticket store and run `ark chief state` while `gate` still blocks.
6. Close the case's descriptor of the `gate` pipe so `gate` ends. Wait for the child to exit. Read its output, the markers and the ticket store, and run `ark chief state` once more.
7. Repeat 1 to 6, each time with a new fixture and a new holder holding 3 cores, for these command lines: `bun test` (no flag, serial: asks 1 core; the holder holds 3, so it waits; step 5 waits for `started-gate` only), `bun test test --parallel=3` (directory argument, the command line of the `ark.yml` cli suite), `bun test --parallel` (bare flag: Bun asks for the CPU count, so the ticket asks min(CPU count, 3); the case reads the CPU count with `os.availableParallelism()`).
8. Repeat 1 to 6, with a new fixture and holder, for `bun test --parallel=3` with cwd a run worktree under `ARK_HOME/projects/demo/runs/<run>/workspace` (not the project `workspace`), once with `ARK_PROJECT=demo` and once with only the path to find the project.
9. With the holder holding 1 of 3 cores, start `bun test --parallel=2`, wait until `started-gate` exists and close the `gate` descriptor: it asks 2 and fits.
10. Start `bun test --parallel=3` under a pseudo-terminal of its own (`Bun.spawn` with `terminal`), with the budget full. Read the terminal output until the waiting line shows, check that no `ran-*` marker exists, release the holder and the gate, wait for exit. Skipped off macOS.
11. Bounded waits (the failure of the wait itself). Each row below has its own fixture and holder, replaces or adds one file, and reaches exactly one failing wait that no earlier wait of the row can excuse: the earlier waits of the row are the ones of steps 2 to 6 and all pass. Every wait of the row runs with the case's own time limit, below the 90 s test timeout. The case ends every process it started by pid when the row is done. The rows are 11a to 11e.
    - 11a, marker never comes. Command line `bun test --parallel=3`. A file `stuck` replaces `a`: it opens `alive-stuck` for writing as the other files do, then blocks reading a named pipe `stuck` that the case holds open and never writes. It never appends `ran-stuck`. Release the holder; wait for `started-gate`, then for every `ran-*` marker of step 5. The wait for `ran-stuck` is the failing one.
    - 11b, a worker never ends. Command line `bun test --parallel=3`. The file `stuck` replaces `a` and appends `ran-stuck` first, then blocks as in 11a, with `alive-stuck` still open. Release the holder and run the waits of step 5. All markers exist, and the worker that runs `stuck` is blocked in it, so its pid differs from the `gate` pid: the wait for the end of that worker's `alive-stuck` pipe is reached and is the failing one.
    - 11c, the waiting line never shows. Command line `bun test` (serial) in a scratch copy with no `bunfig.toml` preload, holder holding 3 of 3 cores: the run never waits and prints no waiting line. The wait for the waiting line in the output of step 2 is the failing one.
    - 11d, the child never exits after the release. Command line `bun test` (serial) with the preload. `gate` reads its pipe until end-of-file as before, then blocks reading a second named pipe `hang` that the case holds open and never writes. Run steps 2 and 5, close the `gate` descriptor as in step 6, then wait for the child to exit: that wait is the failing one.
    - 11e, the output pipe stays open after the child exits. Command line `bun test` (serial) with the preload. A file `leak` replaces `c`: it starts a detached process with the standard output and error of the run inherited, which lives until the case ends it by pid, and records that pid in a marker. Run steps 2, 5 and 6. The child exits 0 (the wait for exit passes); the wait for the end of its output is the failing one.

## Expected results

- Steps 2 and 8: no `ran-*` marker, no `started-gate` before the release. A serial row shows exactly one waiting line while the child still waits. A `--parallel` row over a pipe shows its line when the file of the creating worker ends, so the check of the line is at exit: exactly one waiting line in the whole output, not one line per test file. The ticket (step 3) is the proof of the wait before the release.
- Step 3: one ticket with label `bun test`, waiting; its pid is the pid of the spawned `bun test` and alive.
- Step 4: chief state shows `- waiting: bun test (pid N), 3 cores` with the pid of step 3. This is the reader that the run lead's interim paragraph greps.
- Step 5: the `gate` worker is alive. In a `--parallel` row, every worker that ran a file other than `gate` has exited when the ticket is read. The ticket store holds exactly one ticket for the invocation (not one per file): started, label `bun test`, the cores asked, the coordinator pid, alive, while `gate` still runs. Chief state shows `- running: bun test (pid N)` with the same pid. A ticket freed by any other worker's exit fails here. The ticket's creator is a worker's preload, and a creator that registers exit cleanup is ARK-T155 step 9 ("a helper writes no exit cleanup"), not this step. The ticket of an ended coordinator stays until the next reader prunes it, so the case reads the store through `readTestLock` after the exit, never the directory.
- Step 6: all four files ran exactly once; the child exits 0; the ticket store has no `bun test` ticket; chief state shows no `bun test` entry.
- Step 7: the same for each command line; the serial run asks 1 core, the bare `--parallel` run asks min(CPU count, 3), never above the budget.
- Step 8: both ways to the project wait the same way.
- Step 9: all files run with no wait and no waiting line (cores fit).
- Step 10: the waiting line shows live in the terminal output while no file runs, and exactly one waiting line shows in the whole output.
- Step 11: in each row the one failing wait rejects with an error that names what it waited for (11a the marker `ran-stuck`, 11b the end of `alive-stuck`, 11c the waiting line, 11d the exit of the child, 11e the end of the output), inside its own time limit and below the 90 s test timeout; the case asserts that rejection and its elapsed time, and passes. At the head before this run each of these waits is unbounded: the row fails at its own row test timeout (a limit set on the row, shorter than the 90 s default) and not at a named wait error, so each row is red proof. The rows do not depend on the Linux cause: each state is built on any host.
